# Windows broker connection failure: evidence and acceptance

See [WorkerOwner follow-up](WORKER_OWNER_VALIDATION.md) for the newer real-user
evidence and per-check instrumentation. The original diagnosis below predates it.

## What was demonstrated

The reported desktop failure has **not** been reproduced on that desktop. A 15–25 second delay matches the 15-second IPC deadline plus up to eight seconds of cleanup, but cannot establish why the worker failed. Successful independent HTTPS probes do not validate the broker or Flowseal startup.

Two code defects were established: `ConnectCoreAsync` waited only for IPC, even if its owned bootstrap/worker had already exited; the startup deadline therefore surfaced as generic cancellation and stderr from `runas` was unavailable. `MainViewModel.ApplyStatus` passed an unchanged cached error to `Fail` on each poll. These defects masked early failures and repeated their logs. No timeout was increased.

The fix races each pre-authentication pipe operation against the held query-limited/synchronize process handle. Worker terminal exit codes retain the failing stage even if the evidence connection closes early. Fixed numeric evidence is sent over two separate exclusive local pipes with the existing restrictive owner/SYSTEM/Admin ACL, medium integrity label and remote rejection. Bootstrap evidence requires the exact held PID; worker evidence requires an owned direct child, creation ordering and protected image. Evidence is advisory, **never authentication or command authorization**. Primary IPC still requires elevated same-user/logon/session identity, image/creation/parent validation, nonce challenge and ordered v3 commands. Split capabilities and engine code are unchanged.

Each evidence channel permits at most 32 records / 4096 bytes with 128-character lines. Writes have a 200 ms limit. Diagnostics contain numeric stage, elapsed milliseconds, safe Win32 error or managed HRESULT, worker PID, observed owned helper exit and cleanup state; never challenges, account names, credentials, packet data or command-line arguments. A single atomic local `%LOCALAPPDATA%/Northpass/diagnostics/broker-startup.json` record (64 stages / 16 KiB maximum) preserves the latest failure across desktop restarts; it is advisory and never read to authorize or automatically retry. Journal errors cannot replace the startup failure; elevated callers skip per-user journal writes. Managed error callbacks and polling share one last fingerprint; a changed error, an intervening healthy state or an explicit new connection attempt starts a new event. The existing UI log length limit remains.

Closing the bootstrap evidence lease cancels only its owned kill-on-close job, including before primary IPC authentication. Medium UI never force-kills an elevated process. Cleanup closes IPC/leases, waits at most eight seconds and retains the owned process handle and component file leases if exit cannot be confirmed. A new launch is refused while ownership is pending. Failure cleanup cannot mask the original failure with a process observation error. Bootstrap crash/power loss can still leave a protected session directory for repair; no shared driver/service is stopped.

## Reading an exported diagnostic log

`BROKER_CLIENT` identifies desktop stages: installation validation, shell elevation, pipe wait, peer verification, challenge, component preparation, engine start and ready. `elevation=helper-returned` means Windows returned an owned process; on the real `runas` path this follows approval. It is not proof of broker authentication or engine readiness.

`BROKER_STAGE` is bounded owned-helper evidence. `BROKER_FAILURE` includes `kind`, `stage`, `elapsed_ms`, `code`, `helper_exit` and `cleanup`. `code` is explicitly a safe exception Win32 code or HRESULT (generic native validation is Windows `ERROR_INVALID_DATA=13`); an unavailable code/exit is not inferred from timeout. Helper worker exit family `0x4e50SSKK` and bootstrap family `0x4e51SS01` encode numeric stage `SS`. Worker terminal kind `KK=01` is unexpected failure, `02` is explicit authorization rejection, `03` is invalid data, and `04` is timeout; recognized rejection codes distinguish a failed security check from an arbitrary crash even if its pipe closes early. Stage 3: bootstrap owner; 4: bootstrap protection/hashes; 5: worker creation; 6: worker installation/owner/token; 7: pipe connection; 8: peer identity; 9: authentication; 10: preparing components; 11: starting engine; 12: ready; 13: cleanup. Nonzero observed exit takes precedence over a generic deadline; external cancellation remains separate.

Kinds distinguish shell error 1223 (`UacDenied`), external `Cancelled`, `StartupTimeout`, `HelperExited`, `AuthenticationRejected`, `InstallationRejected`, authenticated `EngineLaunchFailed`, post-authentication `IpcDisconnected`, `CleanupIncomplete` and other `LaunchFailed`. User messages are localized EN/RU/AZ; numeric details stay in Diagnostics. If cleanup is pending, keep Northpass open and inspect the owned helper state; do not start duplicate helpers or alter ACLs/security settings.

## Automated coverage

Portable coordinator and schema tests cover successful startup, helper-exit precedence, shared deadline, external cancellation, denial mapping, authentication errors, malformed evidence, cleanup timeout/retry and error transitions. These are **not interactive UAC tests**.

The Windows published-package acceptance script additionally exercises an actual protected worker rejecting a deliberately renamed desktop owner image before authentication, and actual cancellation after helper return followed by a fresh successful session on the same client. Existing real token/ACL/hash, wrong peer, replay, worker crash, parent death, driver, packet integrity and installer tests remain. These are deliberate fault/security fixtures, not proof that the desktop report has the same cause. CI uses a pre-elevated handoff and never changes UAC policies; it is not secure-desktop approval/denial.

## Manual interactive Windows 10/11 acceptance (not run in cloud CI)

Use a clean Windows 10 x64 and Windows 11 x64 VM or dedicated desktop, a normal split-token administrator account, Defender/Firewall/Secure Boot/UAC unchanged, and the corrected offline installer. Use a different clean attempt for each case. Record OS build, installer build SourceRevision, strategy, approximate timings, safe exported diagnostics and owned helper exit; do not export challenge tokens or unrelated account/traffic data.

1. Install normally under Program Files, launch from the normal shortcut and verify the WPF UI is medium integrity. Independently successful YouTube/Discord/Telegram probes are baseline service observations only.
2. Click Connect and approve the actual secure-desktop UAC prompt. Confirm `helper-returned`, bootstrap integrity, worker owner, pipe, peer, authentication, engine start and ready stages in order (bootstrap and worker records may interleave). Confirm the chosen Flowseal child is owned. A running process does not prove bypass; test website/media/voice separately on an authorized connection.
3. Disconnect. Confirm the engine stops, protected private snapshot cleanup completes, and no owned worker/child remains. Reconnect with Balanced and Simple; do not require an extra repair/download or show stale prior errors.
4. Relaunch, click Connect and select **No** at UAC. Expect localized permission denial, `kind=UacDenied`, code 1223, no helper/engine, completed cleanup and exactly one failure event. Leave Diagnostics open for 30 seconds: unchanged polling must not repeat it. Click Connect and approve: a new attempt may log its own event and succeed.
5. Approve only after a longer human delay. The 15-second IPC deadline starts **after** shell launch returns, not while deciding at UAC. Record the result rather than treating delay alone as denial.
6. In a dedicated test VM, terminate only the identified owned bootstrap/worker before authentication using an administrator debugger. Expect `HelperExited` plus stage/owned exit when observable, prompt cleanup, no child, and clean retry. Never terminate other apps or shared drivers. A debugger-induced stop is deliberate injection.
7. In the test VM suspend only the owned worker during startup. Expect bounded timeout and localized guidance. Cleanup must stop the owned job; if exit cannot be observed, `cleanup=pending` must block another launch while retaining ownership. Release the debugger and verify cleanup/retry. Do not promise termination under arbitrary debugger/kernel interference.
8. Test cancellation/closing the application during startup and active traffic; verify owned processes stop. Test worker termination after authentication: one changed failure event, then manual retry. Do not characterize lost in-flight traffic as lossless.
9. Attempt elevation using another account (credential prompt). It must fail closed on user/logon authorization. Do not broaden ACLs or accept alternate credentials to make this pass.
10. Run the offline installer again to repair a deliberately damaged component in the test VM. Protected path/hash/ACL checks must reject damage before repair. Then approve UAC and retry. Complete install/repair/uninstall acceptance separately.

The issue on the original machine is confirmed resolved only after step 2 succeeds there and the exported stages identify the previous failure. If it still fails, the first failing stage, safe code and helper exit are the next diagnostic input. No real ISP bypass, independent security audit, or desktop Windows/UAC certification is implied by CI.
